# Tensor Core work during GPU rendering

Literature review for GiiGaEngine, 21 November 2026. See the [search log](search-log.md), [source notes](sources.md), and [BibTeX bibliography](references.bib).

**Yes, Tensor Core math and conventional GPU math can run concurrently on the same NVIDIA GPU, including within an SM in controlled experiments.** Independent workloads can also overlap with D3D12 rendering through NVIDIA’s documented CUDA-in-Graphics path. The open question for GiiGaEngine is whether an independently useful Tensor Core job can make progress during a sustained, FP32-heavy rendering pass while meeting a frame-time budget. The sources below support testing that question. They give no transferable estimate of the amount of useful work or the frame-time cost. [ISPA](sources.md#ispa) · [Combo](sources.md#combo) · [CUDA-in-Graphics](sources.md#cuda-in-graphics)

## What “all CUDA cores are occupied” could mean

| Observable condition | Why it matters |
| --- | --- |
| Every streaming multiprocessor (SM) has rendering warps active. | An SM can be active while leaving warp slots or execution bandwidth available. |
| The conventional FP32 arithmetic pipeline is near its measured sustained throughput ceiling and the tensor path is idle in the same interval. | This is the closest measurable version of the hypothesis. The supplemental kernel also needs instruction issue and data movement to feed its matrix operations. |
| Rendering leaves insufficient residency resources for an additional compute block on an SM. | That SM cannot admit the block until the required slots, registers, or shared memory become available. A different kernel shape or shorter work chunks can change the result. |

For D3D12, “CUDA cores” here means the conventional shader arithmetic datapaths that execute the renderer’s HLSL. Tensor Cores execute matrix instructions issued by GPU work. The application submits draws or kernels, and the GPU schedules their work on the SMs. A CUDA stream or a D3D12 queue can make independent work eligible to overlap, with actual overlap depending on scheduling, residency, and contention. A GPU-wide activity percentage alone cannot establish arithmetic saturation or same-SM overlap. [CUDA scheduling](sources.md#cuda-scheduling) · [NVIDIA async compute guidance](sources.md#async-compute) · [Profiling references](sources.md#profiling)

## Closest evidence

| Source | Result and scope |
| --- | --- |
| **Combo** (SoCC 2023) | On an RTX 3090, a paired conventional CUDA and Tensor Core microbenchmark reduced total elapsed time by **44.12%** against the sum of the two solo-kernel durations. A separate, more resource-intensive RT-plus-tensor experiment showed zero or negative makespan improvement for the tested pairs. The end-to-end scheduler used real game traces with substitute NVIDIA OptiX workloads and improved background throughput by **14.0% on average, up to 38.2%** over PilotFish. That result combines several scheduling mechanisms. Combo’s intra-SM policy pairs game RT work with conventional background compute, or pairs two background kernels with each other. [§2.3.1 and Table 3, §4.1 and Fig. 7, §5.1.2, §6.2–6.3](sources.md#combo) |
| **ISPA** (IEEE TC 2023) | Separate CUDA kernels were co-located on an RTX 2080 Ti by tuning block residency and shared resource use. Throughput rose by **15.3%** for workloads with inspectable kernels and **7.1%** for cuDNN workloads versus plain streams, while individual application durations rose **56.3% on average** in the authors’ evaluation. System throughput and foreground latency can move in opposite directions. [Source notes](sources.md#ispa) |
| **Tacker** (HPCA 2022) | The authors fused CUDA-heavy and tensor-heavy work into a single launch and adaptively chose among fused and original kernels. They evaluated on RTX 2080 Ti and V100 and reported **18.6%** average background throughput improvement over Baymax under their latency targets. Reordering and gap-filling also contributed. [Source notes](sources.md#tacker) |
| **FlashAttention-3** (NeurIPS 2024) | On Hopper H100, a single kernel interleaves asynchronous tensor matrix multiply with floating-point multiply-add and exponentials for softmax. It demonstrates instruction-level overlap in a deliberately arranged kernel. [Source notes](sources.md#flashattention-3) |
| **CRISP** (IISWC 2024) | Pan and Rogers identify Tensor Core-heavy DLSS on one frame and floating-point-heavy fragment shading on the next as an opportunity for async compute. Their simulator’s rendering/compute case studies provide evidence about contention. The DLSS pairing is a motivating example. [Source notes](sources.md#crisp) |
| **Atelico** (vendor benchmark) | On an RTX 5080, the same D3D12 raster scene at 4K ran at **123 FPS** alone and **121 FPS** with Llama inference in balanced mode. The vendor reports the rendering cost and gives no concurrent inference throughput or tensor execution trace for this benchmark. [Source notes](sources.md#atelico) |
| **NVIDIA guidance and a shipped-game example** | NVIDIA identifies DLSS alongside acceleration-structure builds as a pairing with complementary datapaths. Its GA102 whitepaper shows one *Wolfenstein: Youngblood* frame on an RTX 3080 using shader, RT, and Tensor Core work. Enabling DLSS also reduces the rendering workload, so the frame-time comparison cannot isolate the benefit of overlap. [Async compute guidance](sources.md#async-compute) · [GA102 Fig. 8](sources.md#ga102) |

PilotFish illustrates an important baseline. Background training can make useful progress by using predictable gaps between rendered frames. Counting work per frame alone would credit those gaps as success even if the tensor job never ran during the targeted rendering pass. Kitsune proposes scheduler changes to make typed kernels co-resident predictably. Its proposal helps explain why a pair of independent queues offers no portable guarantee of same-SM placement. [PilotFish](sources.md#pilotfish) · [Kitsune](sources.md#kitsune)

## Implications for GiiGaEngine

The engine creates a `DIRECT` queue, hands it to NVRHI, and submits the frame’s command list through `RenderContext`. The closest documented route for the proposed experiment is to keep the renderer on its graphics queue and attach a CUDA-in-Graphics (CiG) context to a D3D12 compute queue on the same adapter. NVIDIA documents this setup for TensorRT-RTX and provides a capability check. Its shared-memory limits can affect kernel selection, and the separate graphics and CUDA contexts shown in Nsight can time-slice. Confirm the hardware context and actual overlap in the trace. [RenderDevice.h](../../Source/Core/Render/RenderDevice.h#L47-L62) · [RenderContext.h](../../Source/Core/Render/RenderContext.h#L103-L112) · [CUDA-in-Graphics](sources.md#cuda-in-graphics) · [Nsight context view](sources.md#profiling)

A shader-native route could use a D3D12 async compute dispatch with supported HLSL matrix operations. Microsoft deprecated the original Shader Model 6.9 Cooperative Vector preview in favor of the Shader Model 6.10 linear algebra design, which was still in preview at the time of this review. The engine’s shader manager currently uses FXC and Shader Model 5.1, so this route would require a newer compiler path and target-driver validation. [ShaderManager.h](../../Source/Core/Render/ShaderManager.h) · [Microsoft shader model references](sources.md#hlsl-matrix-operations)

## What the experiment would need to show

1. **Define the claim before measuring.** On one specified GPU, an independent Tensor Core job completes correct outputs during the interior of a rendering interval characterized by high FP32 throughput and low standalone tensor activity. Define the sustained FP32 threshold from an on-device calibration and choose minimum useful throughput and acceptable p95/p99 frame-time penalties before collecting the comparison runs. Log the GPU, driver, clocks, scene, resolution, queue priority, and workload settings.
2. **Use positive and negative controls.** First pair a register-resident FP32 workload with a small, verified Tensor Core GEMM on independent streams in one CUDA context. Compare each alone, both serialized, and both eligible to overlap. Sweep FP32 pressure and block resource use separately. On D3D12, repeat with an FP32-heavy graphics pass, then a measured engine pass. Use private, preallocated auxiliary buffers and keep the foreground work, scene, and resolution fixed across the comparison. For useful work, a small batched inference job on cached inputs is a candidate after the synthetic controls pass.
3. **Prove execution and measure impact independently.** Use a GPU execution timeline to show the auxiliary dispatch executing inside the rendering pass. Verify the tensor instructions or an architecture-appropriate tensor metric, and confirm that rendering sustains the defined FP32 threshold in that interval. Exclude queue wait, idle gaps, and the final drain of the render dispatch. Some Nsight Graphics targets report a combined FP16-plus-tensor counter, so pair it with workload attribution and separate tensor verification. Report correct outputs per second, foreground GPU pass duration, and frame-time percentiles across repeated runs. Use whole-GPU overlap for the engine claim and require finer placement evidence for a same-SM claim. [Profiling references](sources.md#profiling)

Overlap inside the targeted interval would establish that the work can run concurrently. Meeting the throughput and frame-time thresholds would establish practical value for that configuration. A result observed only in frame gaps supports temporal scheduling. A result that disappears under sustained pressure establishes where the opportunity ends on the tested hardware.
